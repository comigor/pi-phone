# Mobile access to live Pi sessions

**Research date:** 2026-11-08  
**Evidence:** official project repositories, documentation, and source only. No blogs or second-hand comparisons. “Attach” below means controlling the **same running process**, not reopening its JSONL transcript in another agent process. One-time host/package setup is allowed; a command inside every Pi session is not.

## Conclusion

**No project verified here satisfies the literal entire requirement. Ovis satisfies most of it if running Pi inside herdr is acceptable.** It provides a structured Pi chat plus the real live terminal, multiple SSH hosts, native Android/PWA clients, and closed-app push alerts. Its initial herdr/SSH/pairing setup is not zero-configuration, and it does not adopt a freestanding Pi process outside herdr.

The two closest alternatives address different priorities:

- **Xpropel/Pi-Remote** is the closest purpose-built, multi-host, vanilla-Pi architecture. A globally installed extension automatically registers each live Pi process with a relay that aggregates devices and sessions. Its mobile UI is web-based and **notifications stop working after leaving the page**; each host also needs a supervised foreground `attach` process (default lifetime 12 hours).
- **Pi Dashboard** mirrors and controls existing Pi TUIs through one globally installed bridge extension, with no per-session command, and supports mDNS, mobile web, and Web Push/FCM. Its fleet story is a server selector/remote bridge rather than seamless zero-config Internet aggregation. Its own Pi-Bolt spike found integration breaks, so vanilla Pi is the safe target.

For a polished native app when **starting sessions through the product** is acceptable, choose **Paseo** (full native Android app) or evaluate **Orca** (native but read-mostly beta). Neither adopts an arbitrary external Pi TUI; their external-session flows discover saved transcripts and resume them in a new process.

## Why RPC/web resumes are not live attachment

Pi’s official RPC mode is a **long-lived subprocess controlled over stdin/stdout**, and the official client calls `spawn`; it is not a protocol for injecting a second UI into an existing interactive TUI ([RPC docs](https://github.com/earendil-works/pi/blob/6e2222a8dda06e3d69fad46d630f152f5873567a/packages/coding-agent/docs/rpc.md#L1-L20), [`rpc-client.ts`](https://github.com/earendil-works/pi/blob/6e2222a8dda06e3d69fad46d630f152f5873567a/packages/coding-agent/src/modes/rpc/rpc-client.ts)). `--session` restores conversation state into that subprocess. This is why Paseo, Orca, and the SDK/RPC web UIs can offer excellent continuation without satisfying same-process attachment. Pi-Bolt’s integration guidance similarly tells external tools to launch `pi-bolt` using Pi’s protocols; it does not add a remote-control plane ([Pi-Bolt integrations](https://pi-bolt.opensec.in/docs/integrations.html)).

## Other candidates checked and not shortlisted

- **[VibeAround](https://github.com/jazzenchen/VibeAround/tree/1654259bbb0e247b52352fa7b53221b75458e34c)** supports Pi/OpenCode launch/resume and several remote surfaces, but its documented external handoff pattern uses a per-session `/vibearound handover` command, so it is not the requested zero-command discovery model ([handoff docs](https://github.com/jazzenchen/VibeAround/blob/1654259bbb0e247b52352fa7b53221b75458e34c/docs/use-cases/claude-remote.md#L21-L23)).
- **[mipsel64/pi-remote-control](https://github.com/mipsel64/pi-remote-control)** controls live Pi/OMP and has Web Push, but requires `/rc` in every session and after `/new`, directly failing the setup constraint ([commands](https://github.com/mipsel64/pi-remote-control#pi-and-omp-commands)).
- **[jacobaraujo7/remote_pi](https://github.com/jacobaraujo7/remote_pi)** likewise requires `/remote-pi` inside each chat ([setup](https://github.com/jacobaraujo7/remote_pi#getting-started)).
- **pi2web** has manually configured multi-backend aggregation but creates SDK-owned sessions on demand ([backend](https://github.com/sxwxs/pi2web/blob/89e5af8d9a08f3da6502750022e1ccfcb33bcd53/src/sdk-backend.ts)); it is not live-TUI attachment.
- For **omp/OpenCode**, Ovis, Paseo, Orca, and Agent of Empires have real integrations. OpenCode’s own server/shared-session architecture is also relevant, but it does not solve vanilla-Pi access and was not allowed to substitute for that requirement.

## Practical recommendation

1. **Test Ovis first** with one Pi-in-herdr session on macOS and one on a 24/7 Linux host. It is the only reviewed option combining same-pane live control, structured chat, multi-host aggregation, Android, and closed-app alerts without per-session Pi commands.
2. If herdr is unacceptable, **test Xpropel/Pi-Remote** and supervise its host `attach` process as a service. Treat the lack of background notifications as the remaining gap.
3. If mobile web is acceptable and vanilla Pi is the main runtime, **test Pi Dashboard**. Install the bridge globally per host, pair/save discovered servers, enable push, and do not assume Pi-Bolt works from the project’s vanilla-Pi evidence.
4. Use **Paseo/Orca** when sessions can be launched through their runtime from the outset; do not use their transcript import as evidence of external live-TUI attachment.

A new project is justified only if the non-negotiable target is **automatic Internet-wide discovery and background Android alerts for arbitrary freestanding Pi/Pi-Bolt TUIs in one aggregated fleet**. The reviewed projects leave that exact combination unimplemented; Ovis, Xpropel/Pi-Remote, and Pi Dashboard are the closest foundations.
